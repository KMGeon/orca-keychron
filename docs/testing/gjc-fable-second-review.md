## Observations below the finding bar (no action required by this gate)

- **One-tick `unknown` when the renderer clock is sampled before the receiver applies a frame.** `Indicator.run` samples `now = time.monotonic()` and then calls `source.indicators(now)`; if the receiver thread applies a frame in between, `_connected` sees `received_at > now` and reports `unknown` for that single 50 ms tick (reproduced deterministically at tracker level: `apply(now=10.000001)` then `indicators(10.0)` → `unknown`, `indicators(10.05)` → `working`). The tracker test suite asserts this backward-clock behaviour on purpose, the window is microseconds every 2 s, and a stray white frame is the worst outcome. Passing `None` (sample under the tracker lock) would remove it. Reported here, not as a finding.
- `serve --slots` defaults to `len(DEFAULT_LEDS)` (12) rather than the saved LED count; `test_serve_uses_saved_custom_socket_and_orca_command` pins this, restore handles the mismatch (slots ≥ `max_slots` fall back to overflow), and `serve` never drives the keyboard.
- `_retired` tombstones are never pruned (bounded by `MAX_IDENTITIES = 65536`); at one identity per `gjc` process this is a documented storage bound, not a runtime defect.
